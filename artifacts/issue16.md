# Issue №16: документы в профиле и замер до / после

Локальные критерии приёмки выполнены: общий F1 redmadrobot вырос, F1 PASSPORT и NATIONAL_ID не снизился, на pii-bench и scenarios-v1 нет ухудшения более 0.01 ни по общему F1, ни по прежним типам. На hidden-v1 общий F1 совпал с baseline.

## Изменение детектора

- Профиль `pii-ru-en-v5`, политика `3.0.0`; новые NER-метки `driver_license`, `birth_certificate`, `military_id`, `medical_policy`, публичные типы строго `DRIVER_LICENSE`, `BIRTH_CERTIFICATE`, `MILITARY_ID`, `OMS`.
- Исходные 11 NER-меток исполняются в своей схеме; второй проход видит все 15 меток, но выдаёт только четыре новых. Одна модель, общий бюджет окон. Группы и фактические схемы записываются в trace.model. Emit/accept не менялись: **0.20 / 0.50**.
- Новые модельные документы проходят проверку формы; слова без номера не принимаются как документ. Явная карта/номер заказа не превращаются в ОМС. Scores и отклонённые кандидаты сохраняются в трейсе с причинами.
- Правила свидетельства о рождении, военного билета и ОМС присутствуют; ОМС теперь принимает и точки между группами. Права различаются по NER и явному названию поля, без объявления любого десятизначного числа правами.
- `PROFILE_PATH` выбирает профиль при старте; старые профили без конфигурации групп используют одну схему. Явный `NER_LABELS` переопределяет группы. `OMS_POLICY` поддерживается в старых профилях; текущий публичный тип — `OMS`.
- Примеры из ревью включены в регрессионные тесты.

## Протокол

Выполнены **8658 настоящих HTTP/GPU-запросов**, по 4329 на профиль, на одинаковых 3841 сессиях. HTTP-ошибок, пропусков сессий или расхождений исходных сессий/эталона между профилями нет. Диалоги разбирает штатный загрузчик, поэтому запросов больше, чем сессий. LLM не вызывалась.

Оба профиля проверены на одном окончательном образе `sha256:d7eedb19622e53a0308531d266c5a2433a655731c8f76798aaa967187dabf854`, GPU NVIDIA GeForce RTX 3060 Laptop GPU 6144 MiB, драйвер 580.178.04. Python 3.11.11, torch 2.6.0+cu124, gliner2 2.1.0, Transformers 4.57.1. Код приложения внутри контейнера побайтно совпал с рабочей копией. Модель и веса прежние, закреплённые в манифесте.

**Baseline** — профиль из `origin/detectors@08990b6860b306a279857e65d65be7d49b3a8181` (`pii-ru-en-v3`, 11 меток). Это ровно источник из команды задания на момент начала работы, а не исходная v1 из отчёта итерации 8. В v3 уже были регулярки трёх документов, поэтому их полнота «до» здесь не нулевая. Новая ветка включает и прежние улучшения v4 адресов/паспортов.

Оценка выполнена штатными `scripts.run_detector` и `scripts.evaluate` из `feat/agent-iter9@1ae3290ea9a308604492dbf97a82f54dec98b072`. run_detector, evaluate и формула evaluation.metrics совпадают с iter8; iter9 добавляет в словарь оценки четыре документа. Единственный патч checkout — добавление двух уже существующих причин кандидатов в схему агента, без изменения метрик или решений.

Метрика задания требует пересечения и правильного типа для TP, схлопывает пересекающиеся находки на эталон, а FP считает вне всех положительных эталонных спанов. Неподдерживаемые типы учитываются отдельно. Это не строгая типизированная метрика один к одному из result_v3/v4. ИНН/СНИЛС в эталоне этого протокола сопоставляются с NATIONAL_ID; публичные отдельные INN/SNILS сервиса не переименовывались ради оценки.

Данные и правила просматривались при разработке; это проверка изменений на заданных наборах, не независимая оценка обобщения. Порог не подбирался. Неудачные пробные конфигурации сохранены отдельно и не включены в таблицы ниже.

## Ограничения и результат новых NER-меток

Новые метки не решили все пропуски: после принятия по форме на redmadrobot права имеют TP 91/371, свидетельства 221/341, военные билеты 190/278, ОМС 58/170. Часть значений содержит неполные, замаскированные или словесные записи. По военному билету итоговая полнота не выросла относительно уже существовавшей регулярки v3; это зафиксированный результат, а не заявленный прирост. Снижение emit ради этих пропусков не применялось.

При прямом добавлении всех меток в одну схему NATIONAL_ID ухудшался. Поэтому пробный вариант отклонён; окончательный профиль сохраняет старую схему для прежних классов, полный контекст для новых и форматную проверку. Критерии проверены заново на полном HTTP-прогоне, без воспроизведения кешированных scores.

## Воспроизведение

Взять checkout оценки по SHA выше, применить [патч схемы агента](issue16-agent-schema.patch), установить его uv.lock с `uv sync --locked --group eval`. Подготовить два сохранённых профиля и одинаковые локальные веса. Перед каждой серией перезапустить сервис с `PROFILE_PATH=/profiles/profile-before.toml` либо `profile-after.toml`; клиентский `--profile` сам по себе профиль сервиса не меняет. Локальный порт замера — 18016.

Из корня checkout оценки для каждого `<before|after>`:

```bash
python -m scripts.run_detector --redmadrobot <data>/test.csv --profile <profile>.toml --url http://127.0.0.1:18016/v1/detect --out runs/detector-<before|after>/redmadrobot.jsonl
python -m scripts.run_detector --data <pii-bench-data> --profile <profile>.toml --url http://127.0.0.1:18016/v1/detect --out runs/detector-<before|after>/pii-bench.jsonl
python -m scripts.run_detector --scenarios data/scenarios/scenarios-v1.jsonl --profile <profile>.toml --url http://127.0.0.1:18016/v1/detect --out runs/detector-<before|after>/scenarios-v1.jsonl
python -m scripts.run_detector --scenarios data/scenarios/hidden-v1.jsonl --profile <profile>.toml --url http://127.0.0.1:18016/v1/detect --out runs/detector-<before|after>/hidden-v1.jsonl
python -m scripts.evaluate --logs runs/detector-<before|after>/<set>.jsonl --out runs/eval-detector-<before|after>-<set>
```

Точные выполненные команды, профили, версии, контрольные суммы, отчёты и JSONL находятся в игнорируемом каталоге `backend/detectors/acceptance-output/issue16/`. В JSONL сохранены сессия, DetectionLog с принятыми/отклонёнными кандидатами и эталон; записи валидированы штатной схемой агента.
