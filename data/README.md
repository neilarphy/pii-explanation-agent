## Контракт v1.0

`schema.py` — исполняемая схема, `example.schema.json` — её JSON Schema.
`examples/synthetic.jsonl` — два вручную созданных синтетических примера без трасс.

- `session_id`, `messages`: ID, роль и исходный текст каждого сообщения.
- `gold_entities`: ID, message_id, entity_type, start/end, точный text.
- `detections`: те же спаны плюс detector, detector_version, confidence и trace.
- `detector_run_id`, `trace_origin`: происхождение результатов (`actual`,
  `unit_test`, `not_run`). Искусственные трассы допустимы только в unit-тестах.
- `gold_verdicts`: TP/FP требуют detection_id, TP/FN — gold_entity_id.
  TN относится ко всей пустой сессии. Смешанные случаи описываются несколькими
  вердиктами, а не единственным классом сессии.
- `source`: dataset, revision, license, source_id, group_id, split, url;
  `metadata` для дополнительных сведений.

Позиции — индексы Unicode code points Python, полуинтервал `[start, end)`
относительно конкретного сообщения. Это не UTF-8 bytes и не UTF-16 JS offsets.
Проверяются границы, точная цитата, ID и ссылки, конечный confidence [0,1],
структура вердикта. Неизвестные поля запрещены; coercion отключён.
`detections: null` = не запускали; `[]` = запуск завершён без срабатываний.
Загрузчик не выводит TP/FP/FN/TN из отсутствующих логов.

`trace` пока расширяемый словарь: он сохраняет исходные сигналы, но не доказывает
правдивость происхождения или полноту причин. Общего формата у backend ещё нет.
Перед интеграцией нужно согласовать с Толей ID/роли/вердикты и Unicode offsets,
с Михаилом — ID запуска, версии, trace, пороги и таксономию. После согласования
добавить адаптер либо вынести контракт в backend/schemas отдельным изменением.
Автоматическое сопоставление сущностей и полнота вердиктов — будущая задача метрик.

## Загрузка и проверка

Из корня репозитория:

```bash
uv sync --locked
uv run python -m data schema data/example.schema.json
uv run python -m data validate data/examples/synthetic.jsonl
uv run python -m data load-redmadrobot --output-dir data/raw/redmadrobot-v1
uv run python -m data validate data/raw/redmadrobot-v1/examples.jsonl
uv run pytest
uv run ruff check .
uv run ruff format --check .
```

В окружениях с read-only home перед командами задать:
`export UV_CACHE_DIR=/workspace/work/uv-cache`.
Для повторного импорта использовать новое имя output-dir: существующий каталог
не перезаписывается. Для offline: добавить `--input /path/to/test.csv`;
локальный источник отмечается `local_unverified` и получает SHA256 — переданная
revision сама по себе не подтверждает происхождение локального файла.

Результаты: source.csv (для HTTP), examples.jsonl, rejections.jsonl, manifest.json.
Revision — фиксированный commit SHA, manifest содержит checksum входа,
версию адаптера, фильтры, число строк/сущностей и политику split.
BIO проверяется строго: orphan I и неизвестные типы отклоняются.
Токены сопоставляются последовательно, без пропуска непробельных символов;
регистр может различаться, исходный текст не меняется. Неустранимые ошибки
попадают в rejection-журнал с индексом строки без текста PII.
Отсутствие строки в результате не является исправлением исходной разметки.

Локальный прогон фиксированной revision: **2841 исходная строка, 2840 приняты,
1 отклонена, 0 дубликатов, 5612 сущностей**. Исходная card заявляет 5614.
Отклонена строка с source_id `1431` (нумерация с нуля): пустой токен.
Она исключена целиком, без автоматической правки двух сущностей.
Это характеристика импорта, не оценка качества детектора.
Манифест без исходных текстов сохранён в `reports/redmadrobot-manifest.json`.

Все импортированные строки остаются в исходном test. Нельзя использовать этот
test для калибровки или подбора порогов. Дедупликация — по точному тексту;
group_id = SHA256 текста. Она не обнаруживает семантические дубликаты и не
восстанавливает неизвестное авторское родство примеров. При генерации диалогов
нужно наследовать group_id родителя и делить по группам до генерации.

## Этап 3: синтетические диалоги

Автономный генератор `synthetic.py` использует контракт v1.0 и только локальные
шаблоны и вымышленные персоны. Redmadrobot и другие внешние данные не читаются,
сеть и LLM не используются. Существующие два fixtures остаются без изменений.

```bash
uv run python -m data.synthetic --seed 42 --groups 40 --variants 2 --output-dir data/raw/synthetic-v1
uv run python -m data validate data/raw/synthetic-v1/train.jsonl
uv run pytest
uv run ruff check .
uv run ruff format --check .
```

Результат: `train.jsonl`, `validation.jsonl`, `calibration.jsonl`, `test.jsonl`
и `manifest.json` с параметрами, SHA256 каждого JSONL, числом групп, примеров,
чистых диалогов и количеством сущностей по категориям. Существующий output-dir
не перезаписывается. При одинаковых параметрах и версии генератора файлы
побайтно одинаковы, включая переводы строк LF; абсолютный путь и время в них не входят.
Минимум — четыре группы и один вариант; по умолчанию получается 80 диалогов.

Каждый четвёртый родительский сценарий не содержит PII. Остальные содержат
FIRST_NAME, LAST_NAME, EMAIL, PHONE, CITY, URL, IP_ADDRESS, PASSPORT, INN,
CREDIT_CARD. Диалоги имеют 4 или 7 сообщений; используются system/user/assistant/tool.
Несколько сущностей встречаются в одном сообщении, email повторяется в ответе.
Спаны строятся при вставке значений, через длину уже собранного текста, без поиска
первого совпадения. Emoji проверяют различие Python code points и UTF-16 offsets.
`detections=null`, `trace_origin=not_run`, вердикты отсутствуют: реальные детекторы
ещё не запускались, чистый диалог сам по себе не получает TN.

`group_id` — SHA256 канонического родителя (версия, seed, индекс, чистота и персона).
Выборка определяется до генерации вариантов: SHA256 от group_id распределяется
по десяти корзинам train/validation/calibration/test с долями 60/20/10/10.
Это выбранные параметры реализации, а не подтверждённые требования команды.
Все варианты персоны наследуют group_id и split. Добавление групп или вариантов
не меняет уже существующие записи и их выборки. Доли приблизительные: для малого
набора отдельные выборки могут быть пусты. Seed входит в идентичность родителя;
разные seed означают разные корпуса, а не повторное разбиение одного корпуса.
Производные примеры нужно сохранять с group_id родителя, не делить заново по строкам.

В режиме по умолчанию `--mode educational` сведения явно учебные: домены `example.invalid`, IP вида `192.0.2.x`, имена
из вымышленных шаблонов, фамилии с уникальным идентификатором. Телефон имеет
тестовый префикс `+0 (000)`, документы и карта — маркеры `TEST-*`, а не действующие
реквизиты. Типы этих маркеров заданы контекстом шаблона. Они не предназначены
для проверки качества распознавания настоящих форматов или контрольных сумм.
Разметка CITY сохраняет таксономию данных и не утверждает конфиденциальность города.
Лицензия сгенерированных примеров обозначена CC0-1.0, источник — локальный генератор.

### Реалистичные синтетические форматы

```bash
uv run python -m data.synthetic --mode realistic --seed 42 --groups 40 --variants 2 --output-dir data/raw/synthetic-realistic-v1
```

Режим `realistic` меняет PHONE, PASSPORT, INN и CREDIT_CARD; остальные категории,
контракт v1.0, точные offsets, роли, чистые сценарии и отсутствие результатов
детектора сохраняются. `educational` остаётся режимом по умолчанию и сохраняет
прежний результат для тех же параметров, включая сериализацию файлов.

- PHONE: международная запись `+44 7700 900xxx` из диапазона
  [Ofcom для вымышленных сюжетов](https://www.ofcom.org.uk/phones-and-broadband/phone-numbers/numbers-for-drama).
  Это британский формат: покрытие российских номеров данным режимом не заявляется.
- PASSPORT: случайные цифры в формате `NN NN NNNNNN`. Контрольная сумма не
  рассчитывается; регион, год серии, выдача и принадлежность документа не проверяются.
- INN: 12 цифр с префиксом 77 и двумя контрольными цифрами. Алгоритм весов
  сверён с [исходным кодом python-stdnum](https://github.com/arthurdejong/python-stdnum/blob/master/stdnum/ru/inn.py),
  библиотека не добавляется в зависимости. Проверяется арифметика номера,
  а не существование записи в реестре или корректность кода инспекции.
- CREDIT_CARD: только `4242424242424242` (Visa) и `5555555555554444` (Mastercard)
  из [официальной документации Stripe](https://docs.stripe.com/testing).
  Номера проходят Luhn и выводятся без разделителей, с пробелами либо дефисами.
  Произвольные PAN не генерируются; CVC и срок действия не добавляются.

Источники проверены 17.11.2026; генерация остаётся полностью offline. Карточные
номера нужны для текстового распознавания, платёжные запросы не выполняются.
Режим и версия реалистичных значений записываются в metadata и manifest,
там же сохраняются ссылки на источники карт и телефонов.

Паспорт и ИНН создаются алгоритмически, без заимствования реальных записей и
без привязки к людям. Они **не объявляются официально зарезервированными тестовыми
номерами**: случайное совпадение с выданным номером исключить нельзя. Корректная
контрольная сумма не подтверждает существование документа. Набор не предназначен
для проверки личности, регистрации или отправки в государственные сервисы.

Оба режима используют неизменный учебный профиль родителя для расчёта group_id
и split, затем realistic подставляет новые значения. Поэтому связанные варианты
обоих режимов остаются в одной выборке. Session/source ID реалистичного режима
имеют отдельный суффикс. Общие тестовые карты и телефоны из ограниченного диапазона
могут повторяться у независимых персон и между выборками; это не оценка обобщения
на ранее не встречавшиеся номера. При изменении seed создаётся другой корпус.

Ограничения: шаблоны общие между выборками, короткие имена и тестовые IP могут
повторяться у независимых персон. Группировка защищает от утечки связанных
вариантов, но не доказывает семантическую независимость или реалистичность корпуса.
Эти данные подходят для проверки контракта и конвейера, но не заменяют независимый
бенчмарк или человеческую разметку. Распределения и объём для экспериментов нужно
согласовать отдельно. Исходный test redmadrobot остаётся исключительно test.
