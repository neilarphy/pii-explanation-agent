# Придите к Богдану со своей постановкой, а не с вопросами

**Главное.** Карточку проекта и слайд 16 не нужно выбирать одно вместо другого: их можно совместить, и это видно из литературы. Агент выдаёт два результата. **(A)** Верное объяснение того, почему детектор сработал, построенное только по трассе каскада. **(B)** Независимый вердикт по спорному срабатыванию: реальный FP, PII действительно есть или пропуск системы, со ссылками на конкретные места в сессии. Ловушка из карточки («верное объяснение воспроизводит ошибку детектора») при таком разделении перестаёт быть проблемой. A верно описывает ошибку, B её ловит. Сравнение grounded / free / hybrid становится абляцией внутри B. Почти всё нужное для MVP уже есть в открытом доступе:
- размеченный корпус `hivetrace/pii-bench` со смещениями спанов и 378 текстами без PII;
- модель GLiNER Guard с поддержкой русского;
- документация HiveTrace о том, что видит админ;
- готовые паттерны «детектор + LLM-верификатор» из SAST/SOC: минус 50–90% FP ценой 3–13% потерянных TP.

Вопросы в анкете, скорее всего, выглядели непроработанными по двум причинам. Большинство просило ментора *решить* за команду: «что такое MVP», «какой baseline». Часть закрывается чтением pii-bench, статьи GLiNER Guard и документации. На созвон стоит прийти с 10 предложениями вида «мы делаем X — подтверждаете?». Отдельно задать вопросы, на которые может ответить только HiveTrace: прод-логи, формат трассы, offsets и scores у GLiNER Guard, доступ к LLM, реальные жалобы админов.

## Что поменялось после ресёрча

Первое: **источник разметки для валидации вердикта уже есть**, отдельный датасет «спорных срабатываний» не нужен. Каскад regex + GLiNER прогоняется по pii-bench, предсказания сравниваются с золотыми спанами, и каждое расхождение автоматически получает метку FP / TP / FN. Готовых датасетов с метками уровня судьи (FP/TP/FN с объяснением) для русского в открытых источниках нет. Значит, это и есть ниша проекта и потенциальная новизна для публикации.

Второе: **«что видит админ» описано в документации HiveTrace**. Карточка записи содержит:
- баннер «Violation detected» со списком сработавших модулей;
- вкладку Data cleansing: замаскированный текст и таблица «тип / имя / число совпадений»;
- вкладку Censors с бейджами Clean / Detected;
- снимок Validation configuration, который не меняется при последующей правке настроек.

Чёрные списки задаются regex-паттернами, белый список называется «Allowed patterns» ([HiveTrace docs: Session details](https://hivetrace.github.io/docs/en/guides/hivetrace-monitoring/session-details/), [Personal data cleaning](https://hivetrace.github.io/docs/en/guides/hivetrace-monitoring/personal-data-cleaning/)). **В документации нет ни потока обратной связи по FP, ни текстового объяснения срабатывания, ни span-офсетов и скоров.** Это и есть пробел, который закрывает агент. Отсюда же вытекает ключевой вопрос: откуда в проде берутся «конкретные места в сессии».

Третье: **ловушка из карточки решается архитектурно, а не метриками**. По Bansal et al. (CHI 2021) объяснения повышают принятие рекомендаций ИИ *независимо от их правильности* ([arXiv 2006.14779](https://arxiv.org/abs/2006.14779)). В RCT Microsoft аналитики с агентом пропустили **46%** подброшенных ложноотрицательных вердиктов агента, без агента 17% ([arXiv 2511.13860](https://arxiv.org/html/2511.13860v1)). «Умное» объяснение, которое тихо исправляет детектор, опасно, поэтому A и B нужно разделять явно.

## Фактура для обзора 5 ноября по четырём направлениям

### Детекторы и данные: на русском модель отвечает только за имена и адреса

**pii-bench** (HiveTraceLab) по карточке датасета:
- **1 810** синтетических русских примеров, сгенерированных Claude Sonnet 4.5 и проверенных вручную;
- сплиты `entity` (910, по 70 на тип) и `domain` (900, по 100 на 9 доменов, из них **378 без PII**);
- 13 типов: NAME, PHONE_NUMBER, EMAIL, ADDRESS, BANK_CARD_NUMBER, CVC, INN, KPP, OGRN, OGRNIP, SNILS, PASSPORT_NUMBER, TOKEN;
- parquet с полями `id, domain, text, entities[{type,start,end,text}]`, лицензия Apache-2.0;
- согласие аннотаторов 0.87 (pairwise exact-span F1) ([HF dataset card](https://huggingface.co/datasets/hivetrace/pii-bench)).

Три детали карточки важны для проекта:
- датасет рекомендовано использовать **только как held-out тест**;
- **идентификаторы имеют валидные форматы и контрольные суммы**, поэтому FP вида «число с битой контрольной суммой» в pii-bench не встретятся, их придётся досинтезировать;
- ADDRESS размечен одним сплошным спаном, а приоритет ADDRESS над пересекающимся NAME искажает рейтинги.

Домены L-CHAT и L-DIALOG помечены как «низкая чувствительность, важнее низкий FP».

**GLiNER Guard** (Minko, Sadiekh, Kokuykin, arXiv 2605.05277, май 2026) построен на GLiNER2 и даёт safety-классификацию и PII-спаны за один проход. Варианты: uni-encoder 147M, bi-encoder 145M, Omni 209M по статье. На HF-карточке у Omni ~307M, расхождение не разрешено. Ключевой архитектурный факт: **в продовом пайплайне структурированные сущности (телефон, карты, ИНН, токены) ловят правила, модель отвечает в основном за Name и Address**. Результаты на pii-bench (pipeline, F1):
- Name **75.7** у uni-encoder против 60.6 у GLiNER2 Multi;
- Address **68.7** у bi-encoder против 52.1;
- «сырой» Address F1 близок к нулю у всех моделей, потому что адрес выдаётся фрагментами и без склейки спанов не засчитывается.

Скорость: 0.020 с на запрос на A100, 193.6 RPS с ONNX TensorRT FP16. Калибровка скоров вынесена в future work ([arXiv 2605.05277](https://arxiv.org/html/2605.05277v1)). Карточка uni-encoder задаёт порог в `schema.entities(..., threshold=0.4)` ([HF](https://huggingface.co/hivetrace/gliner-guard-uniencoder/blob/main/README.md)). **Карточка Omni документирует вывод как «тип → список строк», без start/end и без confidence** ([HF](https://huggingface.co/hivetrace/gliner-guard-omni)). Для «ссылки на место в сессии» это блокер, его надо обсудить с ментором.

**Альтернативы и сверка:**
- **GLiNER2-PII** (Fastino, май 2026): 0.3B, 42 типа, обучена на 7 европейских языках, **русского нет**. Типичная ошибка: принимает организации и продукты за имена людей ([arXiv 2605.09973](https://arxiv.org/html/2605.09973)).
- **«GLiNER 2.5 multi» [не подтверждено]**: скорее всего `fastino/gliner2.5-multi-v1`. Это 287M на mDeBERTa-v3-base, в карточке нет ни русского, ни PII, ни бенчмарков ([HF](https://huggingface.co/fastino/gliner2.5-multi-v1)). Вывод сделан только по названию.
- Второй независимый русский бенчмарк: `redmadrobot-rnd/pii_benchmark` (2 841 предложение, 21 тип, включая ОМС и военный билет, BIO-теги, MIT). Их ruBERT показывает F1 **83.6 → 88.9** с правилами, это ещё одно свидетельство в пользу гибрида ([HF dataset](https://huggingface.co/datasets/redmadrobot-rnd/pii_benchmark), [HF model](https://huggingface.co/redmadrobot-rnd/rubert-base-pii-ner)).
- Контрольные суммы ИНН (10/12), ОГРН/ОГРНИП, СНИЛС, КПП, БИК проверяет `ru-id-validators` (MIT, июль 2026) ([PyPI](https://pypi.org/project/ru-id-validators/)) или `python-stdnum` ([docs](https://arthurdejong.org/python-stdnum/doc/2.0/stdnum.ru.ogrn)). Карты проверяются по Луну.

**Формат трассы готов у Presidio.** С `return_decision_process=True` каждая детекция несёт `recognizer`, `pattern_name`, `original_score` → `score`, `supportive_context_word`, `validation_result`. При этом документация прямо предупреждает, что трасса **объясняет срабатывания, но не пропуски** ([Presidio docs](https://microsoft.github.io/presidio/analyzer/decision_process)).

**DeepPavlov [не подтверждено].** Отдельного PII-репозитория DeepPavlov на GitHub не найдено. Лучшая гипотеза: **SPY** (Savkin, Ionov, Konovalov, NAACL 2025 SRW). Это синтетический англоязычный набор из медицинских и юридических текстов, 7 типов. Гипотеза держится только на совпадении авторов с DeepPavlov 1.0. SPY используется как бенчмарк в статьях GLiNER Guard и GLiNER2-PII ([ACL](https://aclanthology.org/2025.naacl-srw.23), [HF](https://huggingface.co/datasets/mks-logic/SPY)).

### Типичные FP и FN известны заранее

- **Числовая неоднозначность.** В MathEd-PII **64.87%** редактирований провайдера оказались не PII. LLM с промптингом по сегментам сократил ложные DATE больше чем на 99.5% ([arXiv 2602.16571](https://arxiv.org/pdf/2602.16571)).
- **Нестандартные форматы.** «Mind the Gap»: Presidio пропускает email, записанный словами, телефоны с добавочным и карты с «грязными» пробелами ([arXiv 2609.03464](https://arxiv.org/pdf/2609.03464)).
- **Фрагментация спанов** у GLiNER: адреса и ФИО распадаются на куски ([arXiv 2605.05277](https://arxiv.org/html/2605.05277v1)).

Отсюда рабочая таксономия:
- **FP**: номер заказа, сумма или дата вместо ID при битой контрольной сумме; организация или продукт вместо персоны; публичная персона; ИНН юрлица (10 цифр); тестовые и плейсхолдерные данные; ошибка границ спана.
- **FN**: обфускация, нестандартные пробелы, незнакомые адреса, имена в нижнем регистре, обрезка длинной сессии.

### LLM-триаж FP в смежных областях: детектор остаётся, LLM только верифицирует

Сходство схем в SAST и SOC — самый сильный аргумент для постановки. **QASecClaw** оставляет Semgrep генератором кандидатов, а LLM «не ищет новые уязвимости» и работает **fail-open**: при ошибке находка сохраняется. Результат: FP 560 → 64 (**−88.6%**) ценой 40 из 1 273 TP (−3.1%), FPR 0.423 → 0.048. На одном классе CWE верификатор срезал больше TP, чем FP ([arXiv 2605.01885](https://arxiv.org/html/2605.01885v1)). Для нас это означает, что разбивка по типам сущностей обязательна. **ZeroFalse** показывает, что контекст важнее модели: у GPT-5 на OpenVuln F1 растёт с **0.621 до 0.955** только за счёт обогащённого промпта (трасса taint, микро-рубрика, строгий JSON). Открытая gpt-oss-20b даёт F1 0.884 ([arXiv 2510.02534](https://arxiv.org/html/2510.02534v1)). **LASAA** (CMU SEI) использует три вердикта, включая «dependent», и self-consistency: 10 прогонов, вердикт принимается только при согласии не ниже 80%, иначе «uncertain» ([arXiv 2607.09979](https://arxiv.org/html/2607.09979)).

У Semgrep Assistant согласие с экспертами составило **96% на TP, но лишь 41% на FP**. LLM консервативен и неохотно объявляет FP, поэтому метрики нужно считать по классам ([Semgrep](https://semgrep.dev/blog/2025/building-an-appsec-ai-that-security-researchers-agree-with-96-of-the-time/)). **CORTEX** в SOC снижает FPR с 29.8% до 14.2%, но медианная латентность растёт со 45 до 152 с, а токены с 4.2k до 23.6k ([arXiv 2510.00311](https://arxiv.org/html/2510.00311v1)). Microsoft Purview Triage Agent для DLP уже существует: в нём есть класс-воздержание «Not categorized» и объяснение логики, но **нет опубликованных метрик точности** ([MS Learn](https://learn.microsoft.com/purview/copilot-in-purview-agents-overview)).

Прямой PII-аналог — **PII-TRACE** (Perplexity, авг. 2026, многоходовые диалоги). Ошибки детекторов и LLM там взаимодополняют друг друга:
- GLiNER-PII: P **0.261** / R 0.785;
- фронтирные LLM: P ~0.54–0.56, но R только **0.56–0.68**;
- «каждый публичный специализированный детектор» срабатывает больше чем на половине документов без PII ([arXiv 2609.22200](https://arxiv.org/html/2609.22200v1)).

Отсюда вывод: каскад должен быть **асимметричным**. LLM подтверждает или снимает уже найденные спаны. Вердикт «пропуск» принимается только с цитатой, которую код проверяет. Русский язык среди 13 языков PII-TRACE не подтверждён. Опубликованной end-to-end работы «regex/GLiNER → LLM-верификатор» на PII со стоимостью на спан не найдено.

### Верность объяснений: правдоподобие не равно верности, а детектор, в отличие от LLM, можно перезапустить

Базовые результаты:
- у Turpin et al. только **1 из 426** смещённых объяснений упоминало реальную причину смещения ([arXiv 2305.04388](https://arxiv.org/html/2305.04388v2));
- reasoning-модели упоминают использованную подсказку в 25% случаев (Claude 3.7 Sonnet) и 39% (R1) ([Anthropic](https://www.anthropic.com/research/reasoning-models-dont-say-think));
- правдоподобие не коррелирует с точностью симуляции ([Chen et al., ICML 2024](https://proceedings.mlr.press/v235/chen24bl.html));
- Parcalabescu & Frank: для LLM измерима только самосогласованность, а разные тесты расходятся от 1% до 65% ([ACL 2024](https://aclanthology.org/2024.acl-long.329)).

**Преимущество проекта**: объясняемая система — детерминированный каскад, его можно перезапустить. Поэтому causal-concept faithfulness по Matton et al. (корреляция причинного эффекта концепта с частотой его упоминания, [ICLR 2025](https://arxiv.org/html/2504.14150v2)) считается *точно*. Выключаем сигнал, перезапускаем политику и смотрим, перевернулось ли решение.

Метрики переносятся из оценки цитирования:
- **ALCE** даёт citation recall/precision; согласие автоматики с людьми κ = 0.698 / 0.525, это реалистичная планка для валидации LLM-судьи ([arXiv 2305.14627](https://arxiv.org/pdf/2305.14627));
- **FActScore** даёт декомпозицию на атомарные факты ([arXiv 2305.14251](https://arxiv.org/abs/2305.14251));
- **PARENT** даёт оценку текста относительно таблицы без эталона ([ACL P19-1483](https://aclanthology.org/P19-1483/)).

Для human eval пороги Krippendorff α такие: ≥ 0.800 — надёжно, 0.667–0.800 — только осторожные выводы ([Wikipedia](https://en.wikipedia.org/wiki/Krippendorff%27s_alpha)). Rastogi et al. (N = 248 SOC-аналитиков): аналитики принимают выводы ИИ даже при более низкой точности, если объяснение выглядит обоснованным доказательствами, и пропускают длинные объяснения ([arXiv 2503.02065](https://arxiv.org/html/2503.02065v2)).

**open-xai [не найдено].** Публичного «open-xai» Сабрины Садиех нет. Поиск находит только OpenXAI от AI4LIFE (Harvard, NeurIPS 2022), это другой проект, приписывать его лаборатории нельзя ([arXiv 2206.11104](https://arxiv.org/abs/2206.11104)). Ссылку нужно попросить у ментора.

## Предлагаемая постановка: два результата и проверяемые цитаты

**Вход** — одна «спорная» запись: сессия (реплики с направлением in/out), трасса каскада и снимок политики, по образцу Validation configuration. **Выход A** (grounded account) — почему сработало, только по полям трассы. **Выход B** (verdict) — `FP | TRUE_PII | MISSED_PII | UNCERTAIN`, тип сущности, цитаты `{turn, start, end, quote}`, уверенность, рекомендуемое действие (`add_allowed_pattern | add_blacklist | support_ticket | none`) и черновик тикета.

Набросок трассы. Поля взяты из Presidio и Session details, дополнены полями GLiNER:

```json
{"session_id":"s-017","turn":3,"direction":"in",
 "detections":[
  {"id":"d1","stage":"regex","pattern":"INN_12","span":[41,53],"text":"500100732259",
   "checksum":"valid","context_word":"ИНН","allowed_pattern_hit":null},
  {"id":"d2","stage":"gliner","model":"gliner-guard-uniencoder","label":"person",
   "span":[0,14],"score":0.47,"threshold":0.4}],
 "policy":{"mode":"masking","rule":"dataclean.NAME","threat_level":"High",
   "allowed_patterns":["..."],"blacklists":["..."]},
 "decision":"masked"}
```

**MVP к 1 декабря:**
- Python-сервис (API + CLI-отчёт в JSON/Markdown), без фронтенда.
- Каскад: regex по 16 паттернам DataClean с проверкой контрольных сумм, плюс GLiNER Guard uni-encoder для NAME/ADDRESS со склейкой спанов.
- Генератор трассы и агент B с инструментами `get_turns`, `rerun_detector`, `validate_checksum`, `lookup_allowed/blacklist`.
- Строгий JSON, fail-open: при сбое — «PII есть / нужен человек».
- Код-валидатор цитат: подстрока существует по офсету и повторно проходит детектор или контрольную сумму.
- Прогон на двух наборах:
  - автоматически размеченный дифф каскада с pii-bench;
  - собственный dev-набор из ~150–200 спорных кейсов (ловушки с битой контрольной суммой, ИНН юрлица, публичные персоны, плейсхолдеры, обфускация), размеченный двумя участниками команды с подсчётом κ.

Сравнение grounded / free / hybrid (A и абляция входа B) с trace-swap и небольшой human eval переносится на 15 декабря и защиту.

**Метрики B:**
- macro-F1 по трём классам и матрица ошибок;

## Вывод

Новизну проекта стоит формулировать не как «LLM объясняет блокировку». Она в первом **измеренном end-to-end каскаде «regex/GLiNER → LLM-судья» для русского PII** с вердиктами уровня судьи, цитатами, которые проверяет код, и точной (а не оценочной) метрикой верности объяснений. Точной её делает детерминированный детектор, а для LLM такую метрику посчитать нельзя. Литература заранее подсказывает два риска, и стоит назвать их ментору первыми. LLM-судья будет консервативен на FP (96% против 41% у Semgrep) и будет недоверять реальной PII на отдельных типах (провал по одному CWE у QASecClaw). Поэтому стратифицированная оценка и асимметричная метрика «потерянной PII» нужны с первого дня.
